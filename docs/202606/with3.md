# 视频大模型系统 — 整体分析

## 一、系统定位

`my-webui` 是基于 **Open WebUI 二次开发的本地离线视频理解系统**。核心链路：

```
探测元数据 → OpenCV抽帧(质量过滤+pHash去重) → VLM逐帧描述(Ollama/MLX并发)
→ faster-whisper音频转写 → PaddleOCR硬字幕 → qwen2.5汇总 → 输出 .analysis.md / .notebook.md
```

技术栈：OpenCV(抽帧) + Ollama(`qwen2.5vl:7b`视觉 / `qwen2.5:14b`汇总) + faster-whisper(音频) + PaddleOCR(文字)，完全离线、直连本机 Ollama。运行环境为 TencentOS（容器无 systemd，Go 1.20 / Node 18 / Python 3.11）。

**关键架构特征：存在两套并行实现，能力严重不对等**

| 实现 | 文件 | 规模 | 能力 | 谁在用 |
|------|------|------|------|--------|
| **A. 后端 API** | `routers/video_analysis.py` | 1413 行 | 基础抽帧+音频，Web/REST 在线，内存批处理 `_BATCH_JOBS` | 前端 `/video` 面板 |
| **B. 离线脚本** | `scripts/video_tasks.py` | 2348 行 | **全部高级功能** | `video-tasks.json` 驱动 |

`scene_enhanced`、`dedup`、`quality_filter`、`ocr`、`notebook_mode`、`segment` 分段等高级特性**只在脚本 B 实现**。

## 三、对标主流的三大本质差距

| 维度 | 主流做法 | 当前系统 | 差距 |
|------|---------|---------|------|
| **时序理解** | 原生视频模型理解帧间动态/因果 | 逐帧独立描述后文本拼接 | 丢失时序，无"事件"概念 |
| **检索能力** | 帧/字幕向量化，自然语言定位片段 | 仅产出孤立 Markdown | **无向量库、无法跨视频检索** |
| **工程可靠性** | 任务持久化、断点续跑、幂等、失败重试 | 内存字典+文件跳过 | 重启丢状态、规模化难运维 |

辅助差距：音画弱对齐、输出为自由文本（无结构化 JSON，难二次消费）。

## 四、未来整体开发方向

按 **"先增效、再扩能、后检索"** 的优先级（P0 已完成，从 P1 起）：

### 阶段 1 — 海量视频的吞吐与可靠性（最高优先，对应你的核心诉求）
1. **持久化任务队列替代内存字典**：SQLite 任务表，`video_path` 为幂等键，状态机 `pending/running/done/failed`，支持 `--resume`/`--retry-failed`、进程重启恢复。**在 `main()` 外层包裹，不侵入 `run_task` 核心逻辑**，风险最低。
2. **资源感知分级并发**：将流水线拆为 解码(CPU/IO) → VLM推理(GPU串行) → 汇总(GPU) → 写盘(IO) 四级，各级独立并发度，避免 GPU 空转/CPU 抢占。

### 阶段 2 — 省算力 + 架构整合
3. **帧级缓存下沉**：从"整段视频结果缓存"改为"按帧哈希缓存描述"，去重命中帧直接复用，同系列/同模板视频大幅省推理。
4. **统一两套实现**：把脚本 B 的增强能力抽成 `video_core` 公共模块，后端 A 直接复用，消除重复维护这一最大架构债。

### 阶段 3 — 可消费性 + 检索（最大价值杠杆）
5. **结构化 JSON 输出**：报告同步产出时间线/标签/实体/关键帧路径/置信度，便于入库。
6. **轻量时序增强**：汇总 prompt 注入帧时间戳序列 + 镜头边界，让 `qwen2.5` 生成"事件时间线"而非帧堆叠，低成本补时序短板。
7. **RAG-over-video 向量检索**：帧描述+字幕做 embedding 存向量库（venv 已有依赖基础），实现"一句话在海量视频中定位片段"——对标主流的最大增量。
