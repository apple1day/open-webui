# 视频大模型分析系统 — 进度评估与开发方向

## 一、系统当前定位

这是一个基于 **Open WebUI** 二次开发的**离线视频理解系统**，核心是"抽帧 → 视觉模型逐帧描述 → LLM 汇总成报告"。技术栈：OpenCV 抽帧 + Ollama(`minicpm-v` 视觉 / `qwen2.5:14b` 汇总) + faster-whisper 音频 + PaddleOCR 文字。

关键事实：**系统存在两套并行的视频分析实现**，能力严重不对等：

| 实现 | 文件 | 能力 | 你 `video-tasks.json` 用的是它吗 |
|------|------|------|--------|
| **A. 后端 API** | `routers/video_analysis.py` (51KB) | 仅基础抽帧+音频，Web/REST 在线 | 否 |
| **B. 离线脚本** | `scripts/video_tasks.py` (99KB) | 全部高级功能 | **是**（`start-video-analysis.sh` 驱动） |

你配置文件里的 `scene_enhanced`、`dedup`、`quality_filter`、`ocr`、`notebook_mode`、`segment` 等高级特性**只在脚本 B 中实现**。

---

## 二、开发进度 vs 运行进度（关键结论）

功能"写出来了"不等于"跑得通"。我逐行核对了代码，区分两者：

### 已实现且可运行的能力（脚本 B）
- 四种采样模式 `auto/count/interval/scene`
- 增强镜头检测（HSV直方图 + 帧间差 + Canny边缘三维度）
- 帧质量过滤（拉普拉斯模糊/亮度/静态帧）
- 感知哈希去重
- 文件级缓存（路径+时间戳+模型+prompt 的 MD5）
- 并发逐帧推理（ThreadPoolExecutor）
- faster-whisper 音频转写 + .srt
- 笔记模式（education/general/meeting 三风格，带截图嵌入）
- GPU 检测、MLX(Apple Silicon) 后端

### ⚠️ 已写但实际跑挂的部分（已逐行确认）

**缺陷1 — 脚本 `run_task()` 变量"先用后定义"，分段路径必崩 + 普通路径重复抽帧**

`scripts/video_tasks.py` 中：
- 第 **1759 行**分段分支调用 `extract_frames_from_segment()` 时用到了 `_img_dir`、`quality_config`、`dedup_config`、`scene_enhanced`
- 但这些变量在第 **1828–1865 行才定义** → 分段处理（长视频）会直接 `NameError/UnboundLocalError` 崩溃
- 更严重：第 **1818 行**已抽帧一次，第 **1867 行**又用相同参数**重复抽帧一次**，覆盖前面结果

这是典型的多次 AI 编辑叠加未清理。**意味着：长视频分段(`segment`)功能目前完全不可用；普通视频会做两遍抽帧（浪费一倍解码时间）。**

**缺陷2 — 后端 API `VideoAnalyzeResponse` 缺 `status` 字段，收尾必崩**

我已确认 `routers/video_analysis.py` 第 102–114 行的响应模型**没有 `status` 字段**，但 `analyze_video`、`analyze_video_stream`、`_run_batch` 三处都访问 `result.status == 'done'` → `AttributeError`。**后端 API 路径的 `/analyze`、流式、批量在收尾阶段全部失败，历史记录永远写不进。**

### 进度结论
- **离线脚本路径（你在用的）**：核心链路可用，但**长视频分段不可用 + 普通视频重复抽帧**，这恰恰是"海量视频"场景的致命点。
- **后端 API 路径**：基础功能存在但**收尾崩溃**，Web 端的高级体验实际未打通。
- 整体处于"功能堆叠完成度 ~70%，可靠运行完成度 ~45%"的状态。

## 三、对标主流视频大模型分析系统的差距

当前主流方案（如 Video-LLaVA、Qwen2-VL、Gemini 1.5 长上下文、NVIDIA VIA/蓝图、各类 RAG-over-video）已演进到几个方向，你的系统差距点：

| 维度 | 主流做法 | 当前系统 | 差距 |
|------|---------|---------|------|
| **时序理解** | 原生视频模型理解帧间动态/事件因果 | 逐帧独立描述后文本拼接 | 丢失时序，无"动作/事件"概念 |
| **检索** | 向量化帧/字幕，支持自然语言检索定位 | 仅生成 Markdown 报告 | **无向量库、无法跨视频检索** |
| **音画对齐** | 字幕时间轴与画面事件对齐 | 音频/画面分别汇总 | 弱对齐 |
| **结构化输出** | JSON/时间线/实体/标签 | 自由文本报告 | 难以二次消费 |
| **增量处理** | 任务持久化、断点续跑、幂等 | 文件缓存+skip_existing | 无任务状态库 |
| **可观测** | 进度/吞吐/失败重试可视化 | 文本日志 | 海量场景难运维 |

## 四、接下来的开发方向（聚焦海量视频 + 资源整合 + 后台优化）

按"先止血、再增效、后扩能"三个优先级：

### P0 — 止血（1~2 天，不修无法谈"海量"）
1. **修复 `run_task()` 变量顺序与重复抽帧**：把 quality/dedup/scene/`_img_dir` 配置块移到抽帧**之前**，删除第二次 `extract_frames` 调用。
2. **修复后端 `VideoAnalyzeResponse` 缺 `status`**：补字段或改判定逻辑，打通 Web 端历史写入。
3. **清理 `analyze-remote.sh` 硬编码 API Key**（敏感信息，建议同时清理 git 历史）。

### P1 — 海量本地视频的吞吐与资源整合（核心诉求）
这是你说的"处理海量本地视频同时兼顾资源整合"的关键：

1. **引入持久化任务队列替代内存字典**
   - 现状：脚本顺序跑、后端用 `_BATCH_JOBS` 内存字典（重启即丢、最多20个）。
   - 方向：用 **SQLite/Redis 做任务表**（video_path 为幂等键，状态机 `pending/running/done/failed`），支持断点续跑、失败重试、重启恢复。海量视频必须可中断可恢复。

2. **资源感知调度（GPU/CPU/IO 分层并发）**
   - 现状：`concurrency=3` 是粗粒度全局并发。
   - 方向：把流水线拆成 **解码(CPU/IO 密集) → 视觉推理(GPU 密集) → 汇总(GPU) → 写盘(IO)** 四级，各级独立并发度。Ollama 推理串行化（单 GPU 串行更快），解码/抽帧/质量过滤/去重并行化。这样 GPU 不空转、CPU 不抢占。

3. **抽帧与推理解耦 + 帧级缓存下沉**
   - 现状缓存是"整段视频结果"级，改一个参数全部失效。
   - 方向：**帧描述结果按帧哈希缓存**，去重命中的帧直接复用描述，海量相似视频（如同系列/同模板）可大幅省推理。

4. **统一两套实现**：将脚本 B 的增强能力抽成 `video_core` 公共模块，后端 A 直接复用，消除重复维护。

### P2 — 后台功能与可消费性优化
1. **结构化输出层**：报告同时产出 **JSON（时间线/标签/实体/关键帧路径/置信度）**，便于入库与检索。
2. **视频向量检索（RAG-over-video）**：帧描述 + 字幕做 embedding 存向量库（你 venv 里已有大量依赖基础），实现"用一句话在海量视频里定位片段"，这是对标主流的最大价值增量。
3. **轻量时序增强**：在汇总 prompt 中引入帧时间戳序列 + 镜头边界，让 `qwen2.5` 生成"事件时间线"而非帧堆叠，低成本补时序短板。
4. **后台可观测**：任务表 + 简单看板（吞吐/成功率/平均耗时/GPU 利用率），海量场景运维必备。

## 五、建议的推进路线图

```
阶段1 (止血)      修复 run_task 重复抽帧+分段崩溃、后端 status、清理密钥
阶段2 (吞吐)      SQLite 任务队列 + 断点续跑 + 分级并发调度
阶段3 (省算力)    帧级缓存下沉 + 两套实现合并为 video_core
阶段4 (可消费)    结构化 JSON 输出 + 事件时间线
阶段5 (检索)      帧/字幕向量化 + 跨视频自然语言检索
```

**最优先建议**：先做阶段1+2。因为当前"长视频分段崩溃 + 普通视频重复抽帧 + 任务状态不持久"这三点，正好卡在你"处理海量本地视频"的命门上——不解决，规模一上来就会崩或慢一倍。
